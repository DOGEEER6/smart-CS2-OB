这份文件记录的是**踩过坑之后测出来的结论**。每一条都有实测依据，
不是从文档抄的 —— 有几条还和插件文档的说法相反。

## 一、obs-replay-source 插件的真实行为

### 1.1 `ReplaySource.Enable` 会清空缓冲并重新累积

这是"按一下 `←` 就从此刻开始录"能成立的机制基础。

实测：`Disable` → 等 2 秒 → `Enable` → 等 3 秒 → `Load replay`，
拿到的是 **2.97 秒**（= Enable 之后的时长），而**不是** Duration 上限的 5 秒。

所以 `Disable + Enable` 等价于"从现在开始全新录一段"。

### 1.2 `Load replay` 是"快照"，不是自动发生的

插件只是在内存里滚动保留最近 N 秒；**必须先触发 `ReplaySource.Replay` 热键**，
缓存才会变成一段可播放的回放。不按的话回放源里永远是空的。

实测证据：不按热键时截图是 **9 KB 空白帧**，按了之后是 **870 KB** 的真实 CS2 画面。

### 1.3 源级热键必须带 `contextName`

```json
{"hotkeyName": "ReplaySource.Replay", "contextName": "Replay Source"}
```

不带虽然也返回成功，但拿到的片段明显偏短（实测 **1.50 秒**）。
带上之后 OBS 日志会出现：

```
[replay_source: 'Replay Source'] Load replay pressed
[replay_source: 'Replay Source'] replay added of 12.00 seconds
```

### 1.4 缓冲累积的是**游戏渲染帧，不是墙钟时间**

游戏一暂停（甚至只是卡一下），缓冲就饿死。所以"缓冲里有几秒"和"现实过了几秒"
在游戏不流畅时不相等。

### 1.5 每次快照都会"吃掉"缓冲

紧接着再按一次只会拿到很短一段。引擎里因此做了限流：
两次 `Load replay` 之间至少隔 `capture_seconds` 秒。

### 1.6 插件出厂默认值对回放来说是错的

| 设置 | 出厂默认 | 问题 | 应该改成 |
|---|---|---|---|
| `visibility_action` | `Continue (2)` | 源变可见时**不从头播**而是"接着上次"；回放播完后内部 `end=true`，所以**第二次切过去根本不会播** | **`Restart (0)`** |
| `end_action` | `Loop single (2)` | 播完**无限循环**，看完一遍它从头再来 | **`Pause after single (1)`**：播完定格在最后一帧，既不循环也不黑屏 |
| `speed_percent` | `100` | 需要慢放 | `70` |

### 1.7 `source` 可以是**场景名**，不只是源名

插件属性下拉里**同时列出输入源和场景**。本机实际配置：

```json
{"duration": 10000, "end_action": 1, "next_scene": "HUD", "source": "HUD",
 "source_audio": "游戏采集", "speed_percent": 70.01, "visibility_action": 0}
```

`source = "HUD"` 是**场景名**，意味着**回放会带上 HUD 叠加层** —— 这是刻意的，
不是配置错误，**不要"修正"成裸采集源**。

`next_scene = "HUD"` 正好等于直播场景，引擎的"插件驱动切回"就靠它。

### 1.8 两种接法都合法（locale 文件证实）

`G:\obs-studio\data\obs-plugins\replay-source\locale\en-US.ini` 显示：

- **接法 A（推荐，本机在用）**：`ReplaySource` 这个源自己带 `VideoSource` / `AudioSource` 属性
- **接法 B**：给别的源挂滤镜 —— `ReplayFilter` / `ReplayFilterAsync` / `ReplayFilterAudio`

其他关键属性：`CaptureInternalFrames`、`LoadDelay`、`MaxReplays`、
`visibility_action`（Restart / Pause / Continue / None）、
`end_action`（HideAfterSingle / HideAfterAll / PauseAfterSingle / PauseAfterAll / LoopSingle / LoopAll / Reverse…）。

`GetHotkeyList` 里除了 `ReplaySource.Replay`，还有 Next / Previous / Save / Trim / Enable / Disable / NextScene 一整套。

> ⚠️ **不要再相信"回放源上必须有一个 `replay_filter` 滤镜"这种假设。**
> 首次设置向导早期版本就是这么写的：找不到滤镜就 `CreateSourceFilter` 挂到回放源自己身上，
> 还把 `source` / `source_audio` 改成采集源名 —— 这会给一个**本来能用的**系统加垃圾滤镜，
> 还破坏掉 `source="HUD"`。现在的逻辑是：**绝不创建滤镜**，
> `source` 非空且能在（所有输入源名 ∪ 场景名）里解析出来就原样保留。

## 二、键盘钩子的坑

1. **`GetModuleHandleW` 必须设 `restype = c_void_p`**。
   否则 64 位句柄被截断成 32 位，`SetWindowsHookExW` 报 **错误 126**（找不到模块）。
2. **安装钩子和消息循环必须在同一个线程**，否则收不到回调。
3. **小键盘 Enter 和主键盘 Enter 的 `vkCode` 都是 `0x0D`**，靠**扩展位**区分：
   注册键是 `(VK_RETURN, True)` 只匹配小键盘，`(VK_RETURN, False)` 是主键盘。
4. 钩子是 `WH_KEYBOARD_LL` **只读**的 —— 不拦截、不注入、不吞键，所以与 VAC 无关。

## 三、CS2 Game State Integration 的坑

### 3.1 相位必须以 `phase_countdowns.phase` 为准

取值：`live` / `freezetime` / `over` / `bomb` / `defuse` / `timeout_ct` / `timeout_t` / `paused`。
`round.phase` 存在但**不可靠**，只作兜底。

### 3.2 回合结束检测用**水平触发**，不用边沿触发

`phase_countdowns` 和 `map.round` 来自不同子系统，**到达顺序不保证**。
边沿触发会出现"永远不触发"。

### 3.3 `state.round_kills` 会在回合开始时被清零

所以必须**每个数据包都锁存最大值**，否则回合末读到的永远是 0。

### 3.4 CS2 会发"部分包"

某个包里 `allplayers[steamid]` 可能只有 `id` / `team`，
没有 `state` / `weapons`。**必须合并上一包**，否则存活人数会算错（假残局）。

### 3.5 GSI **有**视角朝向

- `allplayers[steamid].position` —— 位置
- `allplayers[steamid].forward` —— **朝向**

朝向角 = `atan2(forward[0], forward[1])`。
（早期文档写"GSI 不提供视角朝向"是**错的**，已更正。）

### 3.6 GSI 里有 `observer_slot`

用它做"该按几号键"的映射：slot `0~8` → 键 `1~9`，slot `9` → 键 `0`。
实测验证：slot 0→按 1、slot 6→按 7、slot 8→按 9。

### 3.7 `weapons` 字典会**残留**以前捡过的枪

实测：`手里 = awp`，栏位却是 `['weapon_knife_widowmaker','weapon_deagle','weapon_awp','weapon_c4']`。
更早还见过"手里是 `glock` 却标 `sniper: true`"。

**所以只认 `state == "active"` 的那把：**

```python
active = next((n for n, s in raw_ws if s == "active"), None)
"sniper": (active in ("weapon_awp", "weapon_ssg08"))
```

这个 bug 不只影响"是不是狙击手"，还会**连带毁掉对枪胜率** ——
拿手枪、栏位里躺着 AWP 的人会被算成 AWP 选手。

### 3.8 多个 GSI 消费者互不干扰

CS2 加载 `cfg` 目录下**所有** `gamestate_integration_*.cfg`，各自 POST 到自己的 `uri`：

| 配置 | 目标 |
|---|---|
| `gamestate_integration_astra_Director.cfg` | `127.0.0.1:23415`（Astra） |
| `gamestate_integration_pwa.cfg` | `127.0.0.1:55599` + token `PERFECTWORLDARENA`（完美世界平台） |
| `gamestate_integration_director.cfg` | `127.0.0.1:23416`（本工具） |

**不需要为了本工具去改 Astra 的配置。**

### 3.9 GSI 配置只该写一个目录

CS2 安装下有两个同名目录，只有一个是真的：

- ✅ `…\Counter-Strike Global Offensive\game\csgo\cfg\` ← **CS2 读这个**
- ❌ `…\Counter-Strike Global Offensive\csgo\cfg\` ← 老版 CS:GO 残留，**不能写**

## 四、回放被腰斩的四个根因

症状：OBS 实测素材 **12.00 秒**，却只播了 7 秒。

1. **定格与播放抢线程**
   `_load_replay` 要读 OBS 日志花 0.5~1 s；期间用户按了播放键，就会读到**上一次的旧素材长度**。
   → 加 `threading.RLock()`，把"决定用哪段素材 + 读长度 + 算时长"整段锁住；
   `_start_replay` 自己读 `self.last_clip_seconds`，不再由调用方传值。

2. **用"文本差异"判断 OBS 日志有没有新行是错的**
   `replay added of 12.00 seconds` 每次文本一模一样，会被判成"没有新行"。
   → 改成按**字节偏移**读新写入的部分（`obs_log_mark()` / `obs_log_since(mark)`）。

3. **长度未知时往短了猜**
   原本用默认 `capture_seconds=5` 估出 8.1 秒。
   → 改成按上限给足，**绝不往短了猜**。

4. **在 obs-websocket 接收线程里发请求 → 死锁**
   `on_obs_event` 回调在接收线程里执行，回调里又发 `SetSceneItemEnabled` / `GetSceneList`
   → 响应要由**同一个被阻塞的线程**来收 → `TimeoutError: OBS 请求超时: SetSceneItemEnabled`。
   → `ObsClient` 加 `self._events = queue.Queue()` + 独立的 `_event_loop()` 线程，
   `_read_loop` 只负责 `put`。

### 收尾顺序不能反

**先切场景，再隐藏源。** 反过来会闪一帧黑屏。

### 让插件自己切回来

preflight 时把 `next_scene` 写成直播场景，由插件在素材播完那一帧
自己 `obs_frontend_set_current_scene`。引擎只负责收尾。
`return_before_end` 因此默认 **0.0**，`on_obs_event` 检测到
「`replay_scene` → `live_scene` 且 replay_active」就 `_end_replay(...)`。
引擎的 `replay_until` 变成 `hold + 5.0` 的兜底。

## 六、静态 GSI 检查脚本

开发期用 Node 的 DOM stub 验证手机端渲染（**没有浏览器可用**时也能测）：

```bat
node --check <提取出来的 JS>        :: 只查语法
node render_test.js                 :: 用真实 GSI 数据跑 render() 并打印生成的 HTML
```

> ⚠️ 测试数据里的向量**必须用逗号分隔**（`"123.45, 678.90, 0.00"`），
> 因为 `parse_vec` 按 `,` 切分。用空格会全部解析成 `None`，
> 然后你会误判成产品 bug 查半天。

## 七、打包 / 交付的坑

1. **单文件 exe 靠 `%TEMP%` 可写。** 一旦被组策略 / 杀软 / 沙箱拦，
   整个程序都起不来，只报一句 `Could not create temporary directory!`
   （`--runtime-tmpdir` 也失败，报 `LOADER: failed to create runtime-tmpdir path …`）。
   → **默认打文件夹版（onedir）**：不落地临时文件，启动快约 1 秒，也不触发自解压拦截。

2. **`websocket-client` 是硬依赖**，没有自研 WS 兜底。PyInstaller 要 `--hidden-import websocket`。

3. **`__file__` 在单文件版里指向临时解包目录** → 口令文件每次重启换内容、手机书签失效。
   → 加 `base_dir()`：`sys.frozen` 时用 `os.path.dirname(sys.executable)`。

4. **双击 exe 时控制台是 GBK(936)**，而代码把 stdout 设成 UTF-8 → 中文全是乱码。
   → 在 `sys.stdout.reconfigure` **之前**调 `console_utf8()`：
   `ctypes.windll.kernel32.SetConsoleOutputCP(65001)` + `SetConsoleCP(65001)`。

5. **`setup_wizard` 是延迟 import**，PyInstaller 静态分析看不到 → 要 `--hidden-import setup_wizard`。

6. **`input()` 在脚本/管道里会崩**（`EOFError: EOF when reading a line`，没有 TTY）。
   → 用 `sys.stdin.isatty()` 判断后再停。

## 八、容易被"好心改坏"的地方

| 改动 | 后果 |
|---|---|
| 收紧 `AIM_ANGLE_DEG` / `AIM_MAX_DIST` | "对枪中"判定少触发 → 最大的加分项（60+130）失效 → 所有人的分都掉下来 → **干脆不切了** |
| 提高 `auto_min_dwell` / 加 `auto_switch_margin` | 同上，表现为"自动切换又迟钝又不准" |
| 把 `DUEL_DOMINANCE` 改回"直接相加" | 架枪的人叠满静态信号能到 243 分，压过真对枪的 190 分 → **镜头从正在打的人身上移开** |
| 把 `DUEL_MAX_DIST` 放宽 | 隔着墙在 1800 单位外互望也被算"对枪中"并锁镜头 |
| 把 `source` 从 `"HUD"` 改成采集源名 | 回放丢掉 HUD 叠加层 |
| 让 `lock_on_manual_scene` 生效 | 用户手动切场景后引擎会抢控制权 |
| 把 `auto_require_focus` 关掉 | 合成的数字键会打进 OBS，乱切场景 |

> 曾经真的踩过第 1、2 条：一次改动同时收紧了 6 个参数（`auto_min_dwell` 2.5→4.5、
> 新增 `auto_switch_margin=18`、`AIM_ANGLE_DEG` 22→20、`AIM_MAX_DIST` 2600→2000、
> 新增 `DUEL_MAX_DIST=1400`、新增 `DUEL_WIN_BONUS=42`），
> 结果自动切换"变得不准而且迟钝"。**修法不是离线瞎调，而是把档位搬到手机上实时调。**
