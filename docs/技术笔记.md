## 一、obs-replay-source 插件的真实行为

### 1.1 `ReplaySource.Enable` 会清空缓冲并重新累积

这是"按一下 `←` 就从此刻开始录"能成立的机制基础。

实测：`Disable` → 等 2 秒 → `Enable` → 等 3 秒 → `Load replay`，
拿到的是 **2.97 秒**（= Enable 之后的时长），而**不是** Duration 上限的 5 秒。

所以 `Disable + Enable` 等价于"从现在开始全新录一段"。

### 1.2 `Load replay` 是"快照"，不是自动发生的

插件只是在内存里滚动保留最近 N 秒；**必须先触发 `ReplaySource.Replay` 热键**，
缓存才会变成一段可播放的回放。不按的话回放源里永远是空的。

实测证据：不按热键时截图是 **9 KB 空白帧**，按了之后是 **870 KB** 的真实 CS2 画面。

### 1.3 源级热键必须带 `contextName`

```json
{"hotkeyName": "ReplaySource.Replay", "contextName": "Replay Source"}
```

不带虽然也返回成功，但拿到的片段明显偏短（实测 **1.50 秒**）。
带上之后 OBS 日志会出现：

```
[replay_source: 'Replay Source'] Load replay pressed
[replay_source: 'Replay Source'] replay added of 12.00 seconds
```

### 1.4 缓冲累积的是**游戏渲染帧，不是墙钟时间**

游戏一暂停（甚至只是卡一下），缓冲就饿死。所以"缓冲里有几秒"和"现实过了几秒"
在游戏不流畅时不相等。

### 1.5 每次快照都会"吃掉"缓冲

紧接着再按一次只会拿到很短一段。引擎里因此做了限流：
两次 `Load replay` 之间至少隔 `capture_seconds` 秒。

### 1.6 插件出厂默认值对回放来说是错的

| 设置 | 出厂默认 | 问题 | 应该改成 |
|---|---|---|---|
| `visibility_action` | `Continue (2)` | 源变可见时**不从头播**而是"接着上次"；回放播完后内部 `end=true`，所以**第二次切过去根本不会播** | **`Restart (0)`** |
| `end_action` | `Loop single (2)` | 播完**无限循环**，看完一遍它从头再来 | **`Pause after single (1)`**：播完定格在最后一帧，既不循环也不黑屏 |
| `speed_percent` | `100` | 需要慢放 | `70` |

### 1.7 `source` 可以是**场景名**，不只是源名

插件属性下拉里**同时列出输入源和场景**。本机实际配置：

```json
{"duration": 10000, "end_action": 1, "next_scene": "HUD", "source": "HUD",
 "source_audio": "游戏采集", "speed_percent": 70.01, "visibility_action": 0}
```

`source = "HUD"` 是**场景名**，意味着**回放会带上 HUD 叠加层** —— 这是刻意的，
不是配置错误，**不要"修正"成裸采集源**。

`next_scene = "HUD"` 正好等于直播场景，引擎的"插件驱动切回"就靠它。

### 1.8 两种接法都合法（locale 文件证实）

`G:\obs-studio\data\obs-plugins\replay-source\locale\en-US.ini` 显示：

- **接法 A（推荐，本机在用）**：`ReplaySource` 这个源自己带 `VideoSource` / `AudioSource` 属性
- **接法 B**：给别的源挂滤镜 —— `ReplayFilter` / `ReplayFilterAsync` / `ReplayFilterAudio`

其他关键属性：`CaptureInternalFrames`、`LoadDelay`、`MaxReplays`、
`visibility_action`（Restart / Pause / Continue / None）、
`end_action`（HideAfterSingle / HideAfterAll / PauseAfterSingle / PauseAfterAll / LoopSingle / LoopAll / Reverse…）。

`GetHotkeyList` 里除了 `ReplaySource.Replay`，还有 Next / Previous / Save / Trim / Enable / Disable / NextScene 一整套。

> ⚠️ **不要再相信"回放源上必须有一个 `replay_filter` 滤镜"这种假设。**
> 首次设置向导早期版本就是这么写的：找不到滤镜就 `CreateSourceFilter` 挂到回放源自己身上，
> 还把 `source` / `source_audio` 改成采集源名 —— 这会给一个**本来能用的**系统加垃圾滤镜，
> 还破坏掉 `source="HUD"`。现在的逻辑是：**绝不创建滤镜**，
> `source` 非空且能在（所有输入源名 ∪ 场景名）里解析出来就原样保留。

### 1.9 `StartDelay` 为负 = 从片段开头裁掉（固定播最后 N 秒靠它）

源码 `replay-source.c`（`C:\Temp\replay-src\replay-source.c`，111,921 B，
从 `https://ghproxy.net/https://raw.githubusercontent.com/Exeldro/obs-replay-source/master/replay-source.c`
下的 —— raw.githubusercontent 直连超时、cdn.jsdelivr.net 连不上）：

- `struct replay` 有 `int64_t trim_front; int64_t trim_end;`（:45-46）。
- `replay_retrieve` :1096-1097 先把两个 trim 清零，
  :1154 `new_replay.duration = last_frame_timestamp - first_frame_timestamp;`
  （**保存下来的就是缓冲里的全部帧**），然后 :1156-1173：

```c
if (context->start_delay > 0) { … }
else if (context->start_delay < 0 && context->start_delay * -1 < (int64_t)new_replay.duration) {
    new_replay.trim_front = context->start_delay * -1;   // ← 负 start_delay → 正的 trim_front
}
```

- 播放侧 `replay_restart_at_begin` :1382-1395：
  `desired_ts = first_frame_timestamp + trim_front; video_frame_position = find_closest_frame(c, desired_ts, false);`
  —— **真跳到入点，不是快进**。
- **`|trim_front| >= 片段总长` 时那个分支不成立 → trim_front 保持 0 → 原样从头播。**
  所以"算过头"最坏结果只是没裁，不会把片子裁没。
- 设置键名 `"start_delay"`（属性面板叫 **StartDelay**，范围 -100000~100000 ms、步长 1000，
  :3046；`SetInputSettings` 不受步长限制，可以写 -7300），
  读取处 :2076 `context->start_delay = obs_data_get_int(settings, SETTING_START_DELAY) * 1000000;`。
- **改这个设置不会重建滤镜、不会冲掉滚动缓冲**：`replay_source_update` :1927 只设
  `context->start_delay`；真正会碰滤镜的只有 `update_filter_settings` :1902-1924，
  而它**只对 duration / sound_trigger / audio_threshold 的变化**才 `obs_source_update(filter, NULL)`。
- `output_flags` 含 `OBS_SOURCE_CONTROLLABLE_MEDIA`（:3148），但**没有 `.media_set_time`**
  （只实现了 duration/get_state/get_time/next/play_pause/previous/restart/stop，:3162-3169）
  → obs-websocket 的 `SetMediaInputCursor` 这条路**走不通**，只能用 StartDelay。

> 因此引擎的裁剪公式（**2026-10-06 起：入点由你按 `←` 的那一刻决定**）是
> `skip = max(0, avail - elapsed)`，写成 `start_delay = -skip*1000`，其中
> `elapsed = now - ReplayDirector.mark_in_at`（按 ← 标下的入点时刻）、
> `avail = min(record_max_seconds, now - _last_snapshot_at)`（滚动缓冲里实际还剩多少 ——
> 缓冲只留最近 `record_max_seconds` 秒，且每次 `Load replay` 都会把它掏空重新累积）。
> `elapsed > avail + 0.2` → 判定"入点已经滚出缓冲"，只提示、`skip = 0` 整段播（不硬裁）。
> 计算只在 `ReplayDirector.clip_skip_from_mark(mark_at)` 一处（单测 `C:\Temp\entry_test.py`）。
> 第一次写入时自检（写值→读回→比对）并打日志，日志出现"入点通路自检失败"就说明插件换版本
> 不认这个键 → 退回从片头播。
>
> **为什么连"固定秒数"也不要了**：用户 2026-10-06（m03280）原话"去掉自动固定，用左右键截取
> 片段，左标记入点，右标记出点，小键盘回车播放"，并明确选了**整段删掉自动定格代码**
> （不是留个开关关掉）。于是这 8 个键全部不存在：`record_mode`、`auto_capture_on_round_end`、
> `capture_after_round_end`、`auto_play_after_capture`、`auto_play_delay`、`snapshot_on_kill`、
> `snapshot_delay`、`play_tail_seconds`；`_tail_seconds()` / `_entry_skip()` /
> `_fire_pending_snapshot()` 三个方法也删了，`on_kill` 现在只打一行 `[击杀]` 日志；
> 新增 `ReplayDirector.mark_in_at` 与 `DEFAULTS["min_clip_seconds"] = 0.3`（手抖门槛）。
> 素材只由 `ManualController.on_mark_out()` 里那次 `_load_replay(None, skip=...)` 产生。
>
> 留档：前后共有**三版**"自动决定入点/时机"的实现，都已删除（写下来免得以后又有人重新发明）：
>
> 1. **锚点 = "决胜击杀"**（用户 2026-10-06 补充定义："镜头切到他身上并且完成最后击杀才算"）：
>    `MatchState._on_gsi` 每个包记下 GSI 顶层 `player.steamid`（= 观察者正在看的选手）到
>    `MatchState.observed_sid`；该包内谁的 `state.round_kills` 涨了就是击杀者，
>    `sid == observed_sid` → `on_kill(..., on_camera=True)` → `ReplayDirector._last_seen_kill_at/round/name`；
>    `_entry_skip()` 优先用它（要求回合号一致），没有才退回 `_last_kill_*`（最后一枪）。
> 2. **多杀/连杀按"串头"对齐**（用户追问"决胜击杀万一是多杀呢？"）：只按最后一枪会把
>    3 杀/4 杀那一串前面的枪裁掉，于是 `on_kill` 里再维护
>    `_seen_streak_start_at/_round/_count/_names`，镜头拍到的相邻两枪同回合且间隔
>    ≤ `entry_streak_gap_seconds`（默认 5.0，CS 连杀窗口就是 5 秒量级）就算同一串，
>    A 两枪 + B 补枪也算一串；锚点取串头。
> 3. **回合结束自动定格 + 固定只播最后 N 秒**：`auto_capture_on_round_end`（默认 True）让
>    `on_round_end` 在回合结束后 `capture_after_round_end`（1.0 s）排一次 `_pending_snapshot_at`；
>    `on_kill` 里 `snapshot_on_kill` 还会按 `snapshot_delay`（1.2 s）**重排**（新击杀覆盖旧排程，
>    所以片尾钉在"最后击杀 + 1.2 秒"）；`play_tail_seconds` 决定从这段定格里再往前裁多少。
>    删掉的理由：用户要自己框入点出点；而且这套在"被锁 / 不在 HUD"时还得配场景守卫才不会
>    把上一回合的好素材冲掉（Replay Source 只留 `MaxReplays` 段），分支和参数都太多。
>
> 前两版删掉的原因：参数多（4 个键）、长度不可预期（取决于这回合打了几杀、镜头在哪、
> 击杀离定格多远），现场不好掐时间。
>
> **`_snapshot_ok` / `_last_snapshot_at` / `last_clip_*` 这几个字段仍然有用**：
> 前者 = "手里有没有裁好的素材"（没裁过按 Enter 只提示），中者 = "缓冲被掏空重新累积的
> 起点"（`clip_skip_from_mark` 靠它算 `avail`），后者 = OBS 实测的真实片段长度。

### 1.10 包装转场（stinger）会吃掉片头，而 API 问不出它的时长

用户实测反馈："转场会覆盖掉前面一部分"。真机探测（OBS 32.2.2）：

```
GetCurrentSceneTransition →
  transitionName     : 转场
  transitionKind     : obs_stinger_transition
  transitionFixed    : True
  transitionDuration : None          ← 固定时长转场，API 不给秒数
  transitionSettings : { "path": "J:/比赛包装/01_Logo_transition_long.mov", ... }
```

- stinger 是**全屏盖住**的包装：从切场景那一刻起压在节目画面上，3.35 秒才放完。
  而回放源在切场景的**同一瞬间**就开始播了 → 前 3.35 秒观众看不到。
- `transitionFixed=True` 时 `transitionDuration` 是 `null`；`GetSceneTransitionOverride`
  这个请求 obs-websocket **根本不支持**（返回 `Your request type is not valid.`）；
  场景集合 JSON（`%APPDATA%\obs-studio\basic\scenes\未命名.json`）里「即时回放」也没写场景级覆盖
  → **唯一可靠的办法是直接读那个 .mov 的文件时长**。
- `mov_duration()`（`replay_director.py` 模块级函数，纯标准库）解析 QuickTime/MP4 的
  `mvhd` box：`p = data.find(b"mvhd") + 4`，version 0 → `timescale = p+12` / `duration = p+16`，
  version 1 → `p+20` / `p+24`，返回 `duration / timescale`。先只读**文件头 2 MB**
  （本机这几个文件的 `moov`/`mvhd` 就在 offset 44 附近，`ftypqt` 紧跟 `moov`），
  找不到再读尾部 4 MB。实测：`01_Logo_transition_long.mov` → **3.35 s**、
  `LT_Replay.mov` → **13.45 s**、路径不存在 → `None`。
- 修法（`_start_replay` → `_freeze_first_frame()`；ticker → `_resume_after_wrap()` →
  `_resume_playback()`）：切场景 + 显示回放源之后**立刻** `TriggerHotkeyByName("ReplaySource.Pause")`
  把画面钉在片段第一帧；等 wrap 秒后由 ticker 调**媒体接口**续播
  （`TriggerMediaInputAction` + `OBS_WEBSOCKET_MEDIA_INPUT_ACTION_PLAY`，对应插件
  `replay_play_pause(data, false)`：只把 `play` 置回 true、把暂停时长补进 `start_timestamp`，
  **同一段素材**从定格那一帧继续）。定格为什么正好停在第一帧：`replay_restart_at_begin`
  :1368-1397 里 `pause_timestamp = c->play ? 0 : os_timestamp` —— 刚显示（`play=false`）就暂停
  → 记下"入点时间戳"。
- ⚠️ **2026-10-06 修掉的大坑：续播绝不能用 `ReplaySource.Replay`。** 现场症状：按 `←` 标的是
  21:43:12~14 的一段，按小键盘 Enter 播出来却是 21:43:44~46（`→` 到 Enter 隔了 27 秒，
  再加 3.35 秒包装转场，偏差一眼就看出来）。根因：插件源码里 `ReplaySource.Replay` →
  `replay_hotkey` :1233-1247 打 `Load replay pressed`，跟的是 `replay_retrieve(context)` :1066
  —— **重新从滚动缓冲取一段素材**，并在取素材那一刻按当时的 `start_delay` 重算裁头
  （:1156-1173）。续播时又取一段"尾巴 = 恢复那一刻"的新素材 → 内容整体后移。
  改法：`_resume_playback()` 发媒体 PLAY；媒体接口不可用时退回 `ReplaySource.Restart`。
- 真机探测（obs-websocket **5.7.4**，脚本 `C:\Temp\media_probe.py` / `media_probe2.py`）：
  `TriggerMediaInputAction`、`GetMediaInputStatus` 都 supported；`GetMediaInputStatus` 对本源
  只回 `mediaState`（`mediaCursor` / `mediaDuration` 是 `None`）；源隐藏且已结束时按
  `ReplaySource.Pause` 热键，状态**仍是 ENDED**（切换式那条"开播"分支不清 `c->end`，
  下一 tick 立刻又结束），而媒体 PLAY / RESTART 都立刻变 `OBS_MEDIA_STATE_PLAYING`
  （媒体动作是异步的，读状态前要等 ~0.3 s）。
  因此 `_freeze_first_frame()` 先 `_wait_media_state` 等 `PLAYING`（最长 0.5 s），
  只有"正在播"或读不到状态才按 Pause。
- 插件关键位置：`replay_play_pause` :722-757（`pause=true` 切换式 / `pause=false` 强制播）、
  `replay_pause_hotkey` :768-775、`replay_restart` :676-682（`restart = true; play = true`）、
  `replay_source_active` :637-655（`visibility_action`：RESTART 0 / PAUSE 1 / CONTINUE 2 /
  NONE 3）、`replay_update_position` :479-537（取完素材
  `start_timestamp = now - trim_front*100/speed`，且只有 `active ||
  visibility_action == CONTINUE` 才 `play = true`）、媒体回调 :3135-3171（**没有 `.media_play`**）。
- 兜底：`replay_until = now + wrap + hold + 5`（引擎掐时间的窗口含等待）；
  `_end_replay()` 清零 `_wrap_resume_at` 取消待恢复，免得切回直播后回放又自己响起来。
- 配置 `replay_wrap_seconds`：`null` = 自动量当前转场；数字 = 强制等；`0` = 回到旧行为。
  非 stinger 转场（淡入淡出等）**完全不等待**。
- ⚠️ **2026-10-06 晚再修：文件时长 ≠ 动画时长。** 用户反馈"播放前会卡零点几秒不动"。
  把 `01_Logo_transition_long.mov` 的 alpha 抽出来逐帧看
  （`ffmpeg -vf "alphaextract,scale=8:8:flags=area" -pix_fmt gray -f rawvideo`，
  201 帧 × 64 字节 = 12 KB）：0.00–0.32 s alpha 6→207 淡入、0.67–2.65 s 恒 251（整屏不透明）、
  2.67–2.98 s 249→6 淡出、**3.00–3.33 s alpha=6 / luma=0 全透明**；最后一张"看得见"的帧是
  第 177 帧 = **2.95 s**。也就是说 stinger 在 `transition_point`(1.0 s) 那一刻节目已经切到
  新场景，动画 2.95 s 就放完了，之后 0.4 s 观众看到的是**定格的回放画面** —— 引擎却还等到
  3.35 s 才开播，那 0.4 s 就是用户看到的"卡住不动"（真机日志：`暂停耗时 0ms`、
  恢复正好 +3.35 秒 → 不是引擎的轮询开销，就是这个等待本身）。
- 修法：模块级 `stinger_visible_seconds(path, duration, transition_point_ms=None,
  ffmpeg_exe=None, transparent_mean=8.0, timeout=30.0)`（`replay_director.py`，紧跟
  `mov_duration()` 之后）：alpha 抽成 8×8 灰度序列写到 `tempfile.mkstemp` 的临时文件
  （跑完 finally 删掉），`fps = 帧数 / 文件时长`（不用再问 ffprobe），从最后一帧往前跳过

### 1.11 `ReplaySource.Save`（小键盘 6 留档）的隐藏前提

- 热键名就是 **`ReplaySource.Save`**（`replay-source.dll` 字符串里有 "Save replay pressed"），

- **`directory` 默认是空的**：属性面板 `obs_properties_add_path(..., OBS_PATH_DIRECTORY ...)`

  → 不写就会拿默认文件名拼出 `/<文件名>.flv` 这种怪路径。**必须在 preflight 里写进去**
  （`GetRecordDirectory` 拿 OBS 录制目录，本机 `E:/Paris2024`；`file_format` 写成
  `回放_%CCYY-%MM-%DD_%hh.%mm.%ss`）。
- 保存通路（源码）：`replay_save` :916-919 先守 `if (context->current_replay.video_frame_count
  == 0) { saving_status = SAVING_STATUS_NONE; return; }`（**没素材时按保存什么都不做，不会崩**）；
  :925 `memcpy(&context->saving_replay, &context->current_replay, ...)` 存的是**当前选中那段**；
  :1010 打日志 `[replay_source: 'Replay Source'] start saving '<文件名>'`（引擎就是轮询这行
  来回报完整路径）；:1024-1034 保存时**同样应用 `trim_front`** → 存出来的片段和回放里看到的一致。
- 编码：`lossless=false` 时 `ffmpeg_muxer` + `obs_x264`（encoder id `replay_h264_recording`）

- **实测（2026-10-06 18:34）**：preflight 调一次把 `directory`/`file_format` 写好，

  ★ 此时引擎的 `_snapshot_ok` 还是 `False` —— 说明**插件的滚动缓冲是自己在持续累积的，
  没按过 `→` 裁过片也照样能存**，原来"必须先定格"的假设是错的，日志措辞已按实测改。

### 1.12 入点窗口只有 `record_max_seconds` 秒，超了就是"莫名其妙的一段"（2026-10-06 真机）

用户投诉原话：**"截取的片段根本不是啊，你自己看看视频目录里的视频，莫名其妙的一段"**。
真机日志把因果讲得很清楚：

```
[21:57:06] ⏺  【← 标记入点】21:57:06
[21:57:19] ⚠️ 入点已经滚出缓冲了（缓冲里只有 10.0 秒，入点到出点隔了 12.4 秒）→ 这一段从头播
[21:57:20] ✔ 素材已裁好（OBS 实测 10.00 秒，整段播）
[21:57:30] 💾 【小键盘 6 保留片段】✔ 已开始写盘：回放_2026-10-06_21.57.30.flv
```

- `←`(21:57:06) 到 `→`(21:57:19) 隔了 **12.4 秒 > 10 秒滚动缓冲** → 开头那 2.4 秒的画面
  在插件里**已经被覆盖、物理上不存在**；引擎按设计退化成"整段缓冲从头播"，
  而缓冲的尾巴就是按 `→` 的那一刻（≈21:57:09–19）。
- 用户想留的是 21:57:06 起的那次交火（`DOGEEER` 在 21:57:07 / 21:57:11 拿第 1、2 杀），
  可回合最后的第 3、4 杀发生在 **21:57:21 / 21:57:23 —— 都在取素材之后**，
  所以文件里当然没有；看起来就是"莫名其妙的一段"。
- 抽帧核对（`ffprobe` + `ffmpeg -ss t -frames:v 1 -vf scale=960:-2`）：
  `回放_2026-10-06_21.57.30.flv` = **3840x2160 60fps h264、4.95 秒、3,387,051 字节**，
  内容 = 观察者视角（`DOGEEER` 拿 AWP，de_dust2，第 6 回合、比分 2:2）在回合中段走位开镜，
  **没有击杀画面** —— 与"缓冲尾巴"的推断完全一致。
- **所以这不是按键错、也不是裁剪错，是物理限制**：缓冲只有 10 秒。
  内存账：OBS 画布 4K，`obs64` 工作集 26.5 GB / 私有 27.6 GB，整机空闲只剩 17.1 GB
  → 4K 下 10 秒原始帧 ≈ 20 GB，`record_max_seconds` **加不上去**（要加就得牺牲分辨率或加内存）。
- 能做的补救是**把窗口可视化**，别让人靠脑子记秒数：
  `ReplayDirector.mark_window()` 用和 `clip_skip_from_mark()` **完全相同的公式**
  （`avail = min(record_max_seconds, now - 上次裁素材的时刻)`、`left = avail - (now - 入点时刻)`）
  算出 `bufMax / avail / markLeft / markAgo / expired / clipReady / clipAgo / lastClipSec / replayActive`，
  `App.on_gsi()` 把它塞进手机 SSE 快照的 `clip` 字段，手机页面顶部渲染成横幅：
  蓝（还早）→ 黄闪 + 震一下（剩 ≤2.5 秒）→ 红闪 + 再震一下（已滚出）→ `✅ 已裁好`；
  同一个入点每级**只震一次**（`clipStage` 0/1/2），倒计时靠客户端 `Date.now()-lastSnapAt`
  自己走，GSI 断流也不会停。

### 1.13 画布分辨率直接决定回放插件的内存：4K → 40 GB，1080p → 12 GB（2026-10-07）

用户原话：**"obs运行时内存占用40g，太不正常了吧，电脑特别卡，是不是内存溢出？"** —— 不是泄漏，是插件的设计。

- 插件的缓冲是**未压缩 BGRA 原始帧**，账可以精确算出来：
  `画布宽 × 高 × 4 字节 × fps × duration秒 × 2`（滚动缓冲 + 已载入片段各一份）。
- **4K 画布**：3840×2160×4 = **33.18 MB/帧** × 60fps = 1.99 GB/s → 10 秒 19.9 GB → 两份 ≈ **40 GB**
  （实测 `obs64` 私有 **40.86 GB** / 工作集 40.07 GB，整机空闲只剩 9.6 GB）。
- **1080p 画布**：8.29 MB/帧 → 5.0 GB/份 → 两份 ≈ 10 GB
  （实测 `obs64` 私有 **12.51 GB** / 工作集 11.54 GB，整机空闲 **38.65 GB**）。
- 另一半卡顿来自每帧的 **GPU→CPU 读回 + memcpy**：4K ≈ **2 GB/s** 常驻，1080p ≈ 0.5 GB/s。
- 判定"不是泄漏"的方法：**100 秒内每 25 秒采一次** `obs64` 的工作集/私有内存，
  五个点 39.98/39.99/40.03/40.01/40.07 GB —— 完全平；私有内存 40.80→40.86 GB。
- 排查口诀：`obs64` 私有内存 ≈ `2 × 画布宽 × 画布高 × 4 × fps × duration秒`。
  插件 `duration` 默认 10000 ms（属性里 1–10 档、步进 1000），`MaxReplays`(=`replays`) 默认 **1**，
  **每多留一份回放就再多一整份缓冲**。注意"游戏本体是 4K"不影响这个账 ——
  缓冲取的是**画布**尺寸（`source` 填的是场景名 `HUD`，场景按画布渲染）。

**降画布工具 `tools/rescale_canvas.py`**（在线改，**不用关 OBS**，可一键还原）：

- 把 14 个场景 / 46 个场景项（含分组子项）的 `positionX/Y`、`scaleX/Y`、`boundsWidth/Height`
  一起乘 `目标/当前`，然后 `SetVideoSettings`。
- **故意不动**：文字源字号、场景项的 `cropLeft/Right/Top/Bottom`、滤镜里的像素值。
  理由：字号是在源纹理里渲染、**再由场景项 scale 缩放**的，item scale 减半后相对大小不变
  （`F/2160 == 0.5F/1080`），改字号会双重缩小；裁剪按**源像素**算，与画布尺寸无关。
- 备份 + 回滚：`--backup`（默认 `C:\Temp\canvas_backup.json`）、`--restore <json>`、
  中途异常自动回滚（连画布一起改回）；`--shots <dir>` 逐场景截图（改前/改后各拍一轮做对比）。
- ★ **最大的坑：OBS 在基础(画布)分辨率变化时会自动按比例缩放整个场景集合的 position/scale。**
  受控实验（`C:\Temp\canvas_probe.py`）：画布 1080p、某项 `scale=1.0` →
  `SetVideoSettings{3840,2160}` → 读回来是 **2.0**；改回 1080p → 又回到 1.0。
  所以脚本必须**先 `SetVideoSettings`、再写绝对值**（`SetSceneItemTransform` 的
  scale/position 是**绝对值**，没有相对语义 —— 用 `C:\Temp\scale_probe.py` 验证过）。
  先写值再改画布 = 被 OBS 又缩一次（第一版就把 46 项缩成了 **1/4**，画面上表现为
  "背景只铺了左上角四分之一"）。
- 另两个 API 细节：`boundsWidth/boundsHeight` **不接受 <1**
  （`OBS 请求失败 SetSceneItemTransform: The field value of 'boundsWidth' is below the minimum of '1.000000'`）
  → 写回前跳过 0 值；`width/height/sourceWidth/sourceHeight` 是 OBS 算出来的**只读派生字段**，别回写。
- 验证方法（改版式这类操作都该这么做）：改前 `--shots` 拍一轮 → 改后再拍一轮 →
  逐对算 **RGB PSNR**：`ffmpeg -filter_complex "[0:v]format=rgb24,scale=1920:1080[a];[1:v]format=rgb24,scale=1920:1080[b];[a][b]psnr"`。
  注意**两个双输入滤镜不能串成 `psnr,ssim`**，会报
  `Cannot find an unused video input stream to feed the unlabeled input pad ssim`。
  结果：14 个场景里 **10 个 PSNR = inf（像素完全一致）**，另外 4 个（HUD / bp / 入场前等待 / 即时回放）
  34–51 dB，差异只来自里面的游戏画面、背景视频、浏览器源在动。
- 副作用（要提前知道）：**存出来的片段分辨率 = 帧分辨率 = 画布**，
  所以从 4K60 变成 **1080p60**（`ffprobe` 实测 `width=1920 height=1080 r_frame_rate=60/1`）。
  推流输出本来就是 1920x1080，观众看到的东西没变。

## 二、键盘钩子的坑

1. **`GetModuleHandleW` 必须设 `restype = c_void_p`**。
   否则 64 位句柄被截断成 32 位，`SetWindowsHookExW` 报 **错误 126**（找不到模块）。
2. **安装钩子和消息循环必须在同一个线程**，否则收不到回调。
3. **小键盘 Enter 和主键盘 Enter 的 `vkCode` 都是 `0x0D`**，靠**扩展位**区分：
   注册键是 `(VK_RETURN, True)` 只匹配小键盘，`(VK_RETURN, False)` 是主键盘。
4. 钩子是 `WH_KEYBOARD_LL` **只读**的 —— 不拦截、不注入、不吞键，所以与 VAC 无关。
5. **小键盘 `6` 与 `→` 在 NumLock 关时完全同码**：小键盘 6 本身是 `VK_NUMPAD6 = 0x66`
   （扩展位 False），但 NumLock 灯灭时 Windows 发的是 `(VK_RIGHT, ext=True)`，
   scancode 同样是 `0x4D` —— **钩子层无法区分**。所以：
   * 键位表里**只绑 `VK_NUMPAD6`**，绝不能绑 `(VK_RIGHT, True)`（那会把真正的 `→` 标出点键劫持成"保留片段"）；
   * 启动时用 `GetKeyState(0x90) & 1`（模块级 `numlock_on()`）检查 NumLock，灯灭就提醒用户；
   * `run_test_keys` 里也打印这个状态，方便现场排查"按 6 怎么变成标出点了"。

## 三、CS2 Game State Integration 的坑

### 3.1 相位必须以 `phase_countdowns.phase` 为准

取值：`live` / `freezetime` / `over` / `bomb` / `defuse` / `timeout_ct` / `timeout_t` / `paused`。
`round.phase` 存在但**不可靠**，只作兜底。

### 3.2 回合结束检测用**水平触发**，不用边沿触发

`phase_countdowns` 和 `map.round` 来自不同子系统，**到达顺序不保证**。
边沿触发会出现"永远不触发"。

### 3.3 `state.round_kills` 会在回合开始时被清零

所以必须**每个数据包都锁存最大值**，否则回合末读到的永远是 0。

### 3.4 CS2 会发"部分包"

某个包里 `allplayers[steamid]` 可能只有 `id` / `team`，
没有 `state` / `weapons`。**必须合并上一包**，否则存活人数会算错（假残局）。

### 3.5 GSI **有**视角朝向

- `allplayers[steamid].position` —— 位置
- `allplayers[steamid].forward` —— **朝向**

朝向角 = `atan2(forward[0], forward[1])`。
（早期文档写"GSI 不提供视角朝向"是**错的**，已更正。）

### 3.6 GSI 里有 `observer_slot`

用它做"该按几号键"的映射：slot `0~8` → 键 `1~9`，slot `9` → 键 `0`。
实测验证：slot 0→按 1、slot 6→按 7、slot 8→按 9。

### 3.7 `weapons` 字典会**残留**以前捡过的枪

实测：`手里 = awp`，栏位却是 `['weapon_knife_widowmaker','weapon_deagle','weapon_awp','weapon_c4']`。
更早还见过"手里是 `glock` 却标 `sniper: true`"。

**所以只认 `state == "active"` 的那把：**

```python
active = next((n for n, s in raw_ws if s == "active"), None)
"sniper": (active in ("weapon_awp", "weapon_ssg08"))
```

这个 bug 不只影响"是不是狙击手"，还会**连带毁掉对枪胜率** ——
拿手枪、栏位里躺着 AWP 的人会被算成 AWP 选手。

### 3.8 多个 GSI 消费者互不干扰

CS2 加载 `cfg` 目录下**所有** `gamestate_integration_*.cfg`，各自 POST 到自己的 `uri`：

| 配置 | 目标 |
|---|---|
| `gamestate_integration_astra_Director.cfg` | `127.0.0.1:23415`（Astra） |
| `gamestate_integration_pwa.cfg` | `127.0.0.1:55599` + token `PERFECTWORLDARENA`（完美世界平台） |
| `gamestate_integration_director.cfg` | `127.0.0.1:23416`（本工具） |

**不需要为了本工具去改 Astra 的配置。**

### 3.9 GSI 配置只该写一个目录

CS2 安装下有两个同名目录，只有一个是真的：

- ✅ `…\Counter-Strike Global Offensive\game\csgo\cfg\` ← **CS2 读这个**
- ❌ `…\Counter-Strike Global Offensive\csgo\cfg\` ← 老版 CS:GO 残留，**不能写**

## 四、回放被腰斩的四个根因

症状：OBS 实测素材 **12.00 秒**，却只播了 7 秒。

1. **定格与播放抢线程**
   `_load_replay` 要读 OBS 日志花 0.5~1 s；期间用户按了播放键，就会读到**上一次的旧素材长度**。
   → 加 `threading.RLock()`，把"决定用哪段素材 + 读长度 + 算时长"整段锁住；
   `_start_replay` 自己读 `self.last_clip_seconds`，不再由调用方传值。

2. **用"文本差异"判断 OBS 日志有没有新行是错的**
   `replay added of 12.00 seconds` 每次文本一模一样，会被判成"没有新行"。
   → 改成按**字节偏移**读新写入的部分（`obs_log_mark()` / `obs_log_since(mark)`）。

3. **长度未知时往短了猜**
   原本用默认 `capture_seconds=5` 估出 8.1 秒。
   → 改成按上限给足，**绝不往短了猜**。

4. **在 obs-websocket 接收线程里发请求 → 死锁**
   `on_obs_event` 回调在接收线程里执行，回调里又发 `SetSceneItemEnabled` / `GetSceneList`
   → 响应要由**同一个被阻塞的线程**来收 → `TimeoutError: OBS 请求超时: SetSceneItemEnabled`。
   → `ObsClient` 加 `self._events = queue.Queue()` + 独立的 `_event_loop()` 线程，
   `_read_loop` 只负责 `put`。

### 收尾顺序不能反

**先切场景，再隐藏源。** 反过来会闪一帧黑屏。

### 让插件自己切回来

preflight 时把 `next_scene` 写成直播场景，由插件在素材播完那一帧
自己 `obs_frontend_set_current_scene`。引擎只负责收尾。
`return_before_end` 因此默认 **0.0**，`on_obs_event` 检测到
「`replay_scene` → `live_scene` 且 replay_active」就 `_end_replay(...)`。
引擎的 `replay_until` 变成 `hold + 5.0` 的兜底。

## 七、打包 / 交付的坑

1. **单文件 exe 靠 `%TEMP%` 可写。** 一旦被组策略 / 杀软 / 沙箱拦，
   整个程序都起不来，只报一句 `Could not create temporary directory!`
   （`--runtime-tmpdir` 也失败，报 `LOADER: failed to create runtime-tmpdir path …`）。
   → **默认打文件夹版（onedir）**：不落地临时文件，启动快约 1 秒，也不触发自解压拦截。

2. **`websocket-client` 是硬依赖**，没有自研 WS 兜底。PyInstaller 要 `--hidden-import websocket`。

3. **`__file__` 在单文件版里指向临时解包目录** → 口令文件每次重启换内容、手机书签失效。
   → 加 `base_dir()`：`sys.frozen` 时用 `os.path.dirname(sys.executable)`。

4. **双击 exe 时控制台是 GBK(936)**，而代码把 stdout 设成 UTF-8 → 中文全是乱码。
   → 在 `sys.stdout.reconfigure` **之前**调 `console_utf8()`：
   `ctypes.windll.kernel32.SetConsoleOutputCP(65001)` + `SetConsoleCP(65001)`。

5. **`setup_wizard` 是延迟 import**，PyInstaller 静态分析看不到 → 要 `--hidden-import setup_wizard`。

6. **`input()` 在脚本/管道里会崩**（`EOFError: EOF when reading a line`，没有 TTY）。
   → 用 `sys.stdin.isatty()` 判断后再停。

## 九、2026-10-06 那场"按 Enter 播老素材"的完整因果链

[17:05:53]    📸 定格素材（回合 1 结束 +1.0s 自动定格）
   … 一路正常到回合 11（17:22:07）…
[17:25:10]    ✔ 播放已定稿的素材（181 秒前存的，不再重新定格）
[17:25:25] 🔒 已锁定自动导播（原因：回放中被切到「数据看板」）—— 手动接管优先

三个独立缺陷叠成这一场事故：

1. **锁没有超时**：`lock()` 只置标志，唯一解锁途径是手动按方向键。Astra 按比赛阶段
   把场景切到「数据看板」→ 回放中场景变化 → `lock()` → 此后整场不解锁。
2. **定格跳过条件带 `locked`**：`on_round_end` 里 `if self.replay_active or self.locked: 跳过`
   → 锁上之后**再也不定格**，`_snapshot_round` 永远停在第 11 回合。
3. **"有素材"判据太宽**：`reuse_snapshot and self._last_snapshot_at > 0` 永远为真
   → 按 Enter 就播 549 秒 / 668 秒前那段。

修法（都在 `replay_director.py`）：
`manual_lock_seconds=45` + `_expire_manual_lock()`（`ticker` 每 50 ms 检查一次，
**回放中不交还**）；定格只跳过"正在回放"；`_start_replay` 加**按回合的陈旧检测**
（`_snapshot_round != last_completed_round` → 当场重新定格）；
另外顺手修了"播完硬切回 HUD"（改成切回**按播放键时所在的场景**，
"别人中途切走"那条分支则只收起回放源、不抢画面）。

> ⚠️ 去掉"被锁就不定格"之后必须补一条**场景守卫**：`on_round_end` 里若
> `require_live_scene` 且 `_current_scene != live_scene`（人在数据看板/中场休息），
> **照样不定格** —— 因为采集源没在渲染，滤镜缓冲是饿的，定格只会拿到空片或极短片，
> 还会把上一回合那段好素材冲掉（Replay Source 只留 `MaxReplays` 段）。
> 这个守卫是"被锁也照常定格"的必要配套，删掉它就会退化成"接管一次，后面全是垃圾素材"。
> （2026-10-06 更新：自动定格连同这条守卫一起删掉了；手动框选不需要它 —— 场景不对时
> 你按 `→` 打的日志会提醒"游戏采集没在渲染"。）


> 附带教训：`_pending_round` 要独立于 `_snapshot_round` —— 前者是"这段待定格的素材属于哪个回合"，
> 后者是"手里已经攒好的那段是哪个回合的"。提前改后者会让第 3 条的陈旧检测失效。

## 十、2026-10-07：内存真相 + 回放开关 + 可改按键 + 图形界面

### 10.1 内存那几 GB 是插件设计，不是泄漏（用户原话："每次使用这个插件都要占用 10g 内存？是哪里的缺陷吗？"）

先给结论：**不是缺陷，也不是泄漏**。obs-replay-source 把最近 N 秒的**未压缩**帧放在内存里，
账可以精确算出来（代码里就是 `estimate_replay_memory()`）：

```
每帧字节 = 画布宽 × 画布高 × 4（BGRA）
占用     = 每帧字节 × 帧率 × 秒数 × 份数
```

| 画布 | 帧率 | 时长 | 每帧 | 每秒 | 一份 | 两份 |
|---|---|---|---|---|---|---|
| 1920×1080 | 60 | 10 s | 7.9 MB | 475 MB | **4.98 GB** | **9.95 GB** |
| 3840×2160 | 60 | 10 s | 31.6 MB | 1.99 GB | **19.9 GB** | **39.8 GB** |

- 和实测完全对得上：1080p 时 `obs64` 私有 **12.51 GB**（OBS 自身约 2.5 GB + 插件 ≈10 GB）；
  4K 时 **40.86 GB**。所以"10 G"就是 **1080p60 + 10 秒 + 两份**。
- **为什么是两份**：滚动缓冲在 `replay_filter` 滤镜里；`Load replay` 把帧**搬**到
  "已取出的那一段"（见 §10.2），于是"正在回填的缓冲 + 已取出那段"同时在内存里。
- **三处会让它静默翻倍的地方**（引擎现在启动时会体检并核对，见 §10.1.1）：
  1. 插件设置 `replays`（面板叫 **Maximum replays**，`replay.h:84`，范围 1~10、默认 1）
     —— 每多留一段就多**一整份**；
  2. 插件设置 `internal_frames`（**Capture internal frames**，`replay.h:107`，默认关）
     —— 换成"内部帧"抓取，通常再多一份；
  3. 场景里有**多个** `replay_source` 实例 —— 每个实例自己攒一份。
- ⚠️ **旧日志的提示是错的**：`replay_director.py` 里原来写"4K 采集下 10 秒约 7.5 GB、
  1080p 约 1.9 GB"（差 5 倍）。就是这句让人以为"内存溢出"。2026-10-07 已按上面的公式改成
  实时计算，并在启动时打印真数字。
- 想更省：`record_max_seconds` 10→5 秒（省一半）、画布/帧率降一档、
  **或者干脆关掉回放功能**（下一个 §）。

#### 10.1.1 启动时的内存体检（`ReplayDirector._memory_audit()`）

每次 preflight 都会（`memory_report=true` 时）：

1. `GetVideoSettings` 拿真实画布/帧率（**只查一次并缓存**，因为手机页面 10Hz 也要用这个数）；
2. 按上面的公式打印"每帧 / 每秒 / 一份 / 稳态几份"；
3. 读插件的 `replays` / `internal_frames` / `duration` 并逐条点评（多了多少 GB）；
4. `GetInputList` 数 `replay_source` 实例（>1 就警告）；
5. `memory_autofix=true`（默认）时把 `replays` 写回 1、`internal_frames` 写回 false。

单独的体检命令：`python replay_director.py --memory-report` 或双击 `9-memory-check.cmd`。

### 10.2 `Enable` / `Disable` / `Clear` 的真实语义（源码逐行核对，这是"回放开关 + 省内存模式"的地基）

`replay-source.c` / `replay.h`（2026-10-07 从 `cdn.jsdelivr.net/gh/exeldro/obs-replay-source@master`
下的 111,921 B 版本，和 §1.9 那份是同一份）：

- **`ReplaySource.Disable`**（`:2313` 注册，`:1262-1273` 处理）→ `c->disabled = true;
  obs_source_update(source, NULL)` → `replay_source_update` 里 `:2012-2019` 走
  `obs_source_filter_remove(s, context->source_filter)` —— **把 `replay_filter` 从采集源上摘掉，
  内存里那份滚动缓冲真的被释放**。这是"关掉回放功能就能把那几 GB 还回去"的依据。
- **`ReplaySource.Enable`**（`:2317` 注册）→ `disabled = false` → `:2092-2114` 重新
  `obs_source_filter_add(...)`，缓冲**从零开始累积**（配合 §1.1 的实测：Enable 之后攒多久就只有多久）。
- **`Load replay`（`ReplaySource.Replay`）** → `replay_retrieve()` `:1098-1112`：
  `circlebuf_pop_front(&vf->video_frames, &frame, ...)` 把帧**搬**进 `new_replay.video_frames`
  —— 是"移走"不是"复制"，所以取完之后滤镜被掏空、重新累积（§1.5 的"掏空效应"就是这个）。
  稳态两份的来源也在这里。
- **`ReplaySource.Clear`**（`:1610-1630`）→ 把 `replays` 里所有已取出的段 `replay_free_replay()`
  释放掉；`Remove` 只删当前那一段。
- `replay_free_replay` `:539-565` 会先判断"这些帧是不是还挂在 `saving_replay` 上"
  （`:543`），是就不释放 —— 所以按小键盘 6 存盘时**不会**再多出一份帧内存（只是结构体复制）。
- 因此引擎的三个动作对应关系是：
  | 引擎动作 | 插件热键 | 效果 |
  |---|---|---|
  | `arm_capture()` | `ReplaySource.Enable` | 开始攒帧（省内存模式下按入点键时调） |
  | `release_capture()` | `ReplaySource.Disable` | 释放滚动缓冲那一份（裁完片段立刻调） |
  | `clear_replays()` | `ReplaySource.Clear` | 释放"已取出的那一段"（关回放功能时调） |

#### 省内存模式（`replay_mode="armed"`，默认）

```
平时           插件 Disable        →  ≈0 占用
按 ←（入点）   Enable              →  开始攒帧，片段从这一刻开始
按 →（出点）   Load replay → Disable（free_buffer_after_clip=true）
                                   →  帧已经搬到"已取出那段"，只留最近这一段
```

- 代价说清楚：这个模式里 **`←` 不能往回标** —— 它不再"记住过去某一刻"，而是"从现在开始录"。
  这正是项目一贯推荐的打法（"打之前按 ←"），所以现场体验不变；但如果你习惯打完才补按 `←`，
  就用 `buffer` 模式（或者把 `replay_mode` 切回 `buffer`）。
- `clip_skip_from_mark()` 因此分两条路：armed 下 `skip = max(0, elapsed - record_max_seconds)`
  （只有攒过头、开头被覆盖时才裁）；buffer 下还是原来的 `skip = avail - elapsed`。
- 手机页面的顶部横幅也分了文案：armed 下是"正在攒帧 x 秒 / 还能攒 y 秒"，
  到 `record_max_seconds` 才变红（含义是"开头要被覆盖了"，不是"入点滚出缓冲了"）。

### 10.3 回放功能总开关（`replay_enabled`，默认 **false**）

用户要求："replay 功能可选开启或关闭，在图形化界面选择，默认关闭"。

- 关掉时：`ManualController._replay_off()` 让四个键只打一行提示；`set_replay_enabled(False)`
  会顺手 `release_capture()` + （`clear_replay_on_disable=true` 时）`clear_replays()`。
- 打开时：armed → 提示"按入点键才开始攒帧"；buffer → 立刻 `Enable`（并冲一次旧缓冲）。
- **不影响**手机提示器与自动切观察位（那两件事只读 GSI，与回放并列）。
- 三个入口都走 `App.set_feature()` 这一条路（改完 `persist_config()` 写回 config.json）：
  图形界面勾选框、手机页面顶部大开关、命令行 `--replay on/off`。
- 手机页面的新端点是 **`/feature?k=TOKEN&replay=1|0&mode=armed|buffer`**，
  和 `/auto` 一样**必须带口令**（它会动 OBS）。`/state`、`/events` 依旧只读、不带口令。

### 10.4 键位可配置（`keys`）

- 结构：`{"动作": ["键名", ...]}`，动作固定四个（`KEY_ACTIONS`：
  `mark_in` / `mark_out` / `save` / `play`），每个动作**可以绑多个键**。
- 键名表 `KEY_TABLE`：方向键、`space/tab/enter/numpad_enter/numpad0..9/f1..f24/a..z/0..9`
  和常见符号键；也接受 `vk:0x41` / `0x41` / 十进制。反向名由 `key_token_name()` 给。
- **扩展位只有 0x0D 这一族必须区分**（主键盘 Enter / 小键盘 Enter 的 vkCode 都是 0x0D）；
  其它键都绑成"不区分扩展位"的裸 vkCode（`binding_of_token()` 返回 `int` 还是 `(vk, ext)`）。
  这样用户把播放键改成 `f8`、`space` 都不会踩扩展位的坑。
- 冲突策略：同一个键被两个动作绑 → **后者忽略并报告**；键名认不出 → 忽略那一个并报告；
  某个动作一个可用键都不剩 → 退回默认值并报告。**任何情况下四个键都不会一起失灵。**
- 键位来自配置，所以 `make_manual_hook(controller, cfg)` 每次都按当前 cfg 装钩子；
  连日志都用 `ManualController.k` 里当前绑定的键名，不再写死"小键盘 Enter"。
- 单次按键捕获 `KeyCapture`（图形界面点「修改」/ `--set-keys` 用）：
  * 临时装一个 `WH_KEYBOARD_LL`（同样**只读**、不吞键）；
  * **修饰键不算**（`Shift/Ctrl/Alt/Win` 及左右变体），`Esc` = 取消，10 秒超时；
  * 消息循环用 `PeekMessageW` + `sleep(0.02)` 而不是阻塞的 `GetMessageW`
    —— 低级钩子必须抽消息才收得到回调，用 Peek 才能顺便检查"超时/取消"。

### 10.7 存出来的文件为什么这么大？（2026-10-07 用户追问："相机 10 秒 4K 也没这么大，编码有问题吧"）

**先给结论：编码没坏，但插件只有两条通路，其中一条会把体积放大几十倍 —— 那条默认必须关掉。**

插件源码 `replay-source.c:777-806`（逐行核对，1.8.1）：

| 通路 | 触发条件 | 容器 | 视频编码 | 音频 | 量级（4K60 十秒） |
|---|---|---|---|---|---|
| **非无损（默认）** | `lossless = false` | **`.flv`**（`ffmpeg_muxer`） | **`obs_x264`：CRF 23 / preset veryfast / profile high**（`:792-799`） | `ffmpeg_aac` | **20 ~ 60 MB** |
| **无损** | 插件里「Lossless」打开 | **`.avi`**（`ffmpeg_output`） | **`utvideo`**（无损帧内） | `pcm_s16le` | **1 ~ 2.5 GB** |

- **`utvideo` 是无损帧内编码**：整帧不压缩丢弃，4K60 ≈ 100~250 MB/s → 10 秒就是 GB 级。
  这就是"比相机视频大几十倍"的唯一来源。**引擎 preflight 会自动把 `lossless` 纠回 false**
  （`_memory_audit()` 里已有，2026-10-07 又在保存回执里补了一次：只要看到 `.avi` 就现场再纠一遍并打警告）。
- **`.flv` 那条是 CRF（恒定质量）不是恒定码率** —— 画面越花、画布越大，文件就越大，
  典型 CS2 4K60 十几到几十 Mbps，**和手机 4K60（≈50 Mbps）同量级**，谈不上编码有问题。
- 历史实测对得上：`回放_2026-10-06_18.34.09.flv` = 8,491,191 B / 约 8 秒 ≈ **8.5 Mbps**（4K）；
  `回放_2026-10-06_21.57.30.flv` = 3,387,051 B / 4.95 秒 ≈ **5.5 Mbps**（4K）。都很小。

**新增的"体积体检 + 可选后处理"**（`ReplayDirector._postprocess_save()`）：

- 每次按小键盘 6 之后，等文件写完（大小连续两次采样不变）→ 打印
  `📦 文件体积：xx MB（xx 秒）` + `📊 码率约 xx Mbps`，并在 >80 Mbps 时给出"比手机还高"和缓解建议；
- 看到 `.avi` → 报警 + **自动关 Lossless**（实测已发 `SetInputSettings {lossless:false}`）；
- `save_postprocess`（默认 `off`）：
  * `remux` = `-c copy` 换容器 `.flv → .mp4`（零质量损失、秒级，Windows 上更好播）；
  * `reencode` = `libx264 -crf save_postprocess_crf(26) -preset veryfast -c:a aac`，
    压小但慢；原 `.flv` 由 `save_keep_original` 决定留不留（默认删）。
  * 没装 ffmpeg → 只打一行"跳过"，**原文件不动**（绝不因为后处理失败丢素材）。
- 测试：`D:\dsh\_tmp\test_savepost.py`（本机没装真 ffmpeg，用一个 `ffmpeg.cmd` 桩）覆盖 8 个场景 ——
  正常 flv 报体积/码率、`.avi` 报警并真发关 Lossless 请求、off 不产生文件、
  remux 出 `.mp4`、reencode 出 `_small.mp4` 且删原文件、无 ffmpeg 时优雅跳过、写盘未完成时不处理。

### 10.9 每次开播前自动往 CS2 控制台输入指令（2026-10-07 用户要求）

用户原话："新增默认指令选项，允许用户填写每次开播前在 cs 客户端控制台默认要输入的指令（支持多条）"。

**机制**：和自动切观察位**同一套** `SendInput` + 扫描码通路（不注入游戏进程、不碰内存），
只是这次逐字符打：

```
按一下"控制台键"（默认 ` ）→ 等 cs_console_delay_ms → 每条指令逐字符打完再敲一次回车
→ 每条之间停 cs_console_gap_ms → （默认）再按一下控制台键关掉
```

- 字符表 `CHAR_SCANCODE`：**按美式布局**把 0x20–0x7E 全部可打印 ASCII 映射成
  `(Set 1 扫描码, 是否需要 Shift)`；大写字母和 `_ + { } | : " < > ? ! @ # $ % ^ & * ( ) ~`
  都会自动按住左 Shift（`SC_LSHIFT = 0x2A`）。自测覆盖了 95 个可打印字符，**一个不缺**。
- 控制台键 `resolve_console_key()` 既接受单个字符（`` ` `` `'` `\`），也接受键名
  （`f10` / `backtick` / `numpad_enter` / `insert`…），编辑键/方向键会自动带扩展位
  （`KEYEVENTF_EXTENDEDKEY`）。
- **安全阀**：`cs_console_require_focus`（默认 True）→ 只有前台进程是 `cs2.exe` 才发键，
  否则**一个字都不发**（否则那些字符会打进 OBS / 浏览器 / 聊天窗口）。
  仿真回归里显式验了这一条：前台是 `obs64.exe` 时发出的按键数 = 0。
- **三种触发时机** `cs_console_trigger`：
  * `start`（默认）：引擎起来后起一个后台线程，等 CS2 到前台再发（最长 `cs_console_timeout_s`，默认 900 秒）；
  * `round1`：每场第 1 个冻结时间发一次；
  * `manual`：只手动 —— 设置窗口的「现在发送一次」按钮，或 `GET /control/console`。
- 指令解析：空行、`//`、`;` 开头的行忽略；**同一行用 `;` 分隔的多条原样保留**
  （CS 控制台本身就支持 `;` 连写）。日志把每条实际发出去的原文回显，字符打不出来会标注。

⚠️ **踩到的坑（自测抓到的真 bug）**：`round1` 模式下，冻结时间的 GSI 是 **10Hz**，
而"发完一遍"要好几秒 —— 原来的节流只在 `send_now()` **结束时**才记 `_last_sent`，
于是第一条还没打完就被下一个包又触发一次（会连发十几次）。
修法是**先占位再起线程**：`if self._busy or time.time() - self._last_sent < 1800: return`
然后立刻 `self._last_sent = time.time()`。

**另一种做法（不想用按键注入的话）**：把这些指令写进 CS2 的
`<CS2>\game\csgo\cfg\autoexec.cfg`，游戏启动时会自己执行 —— 零注入，
但只在游戏启动那一刻生效，而且需要自己确认 CS2 有没有带 `+exec autoexec` 启动。
本工具选择按键注入，是因为"每次开播前"往往游戏已经开着、而且要能随时手动补发一次。

### 10.6 踩到的坑（2026-10-07）

0. **`--hidden-import websocket` 会在没装依赖时"静默跳过"** —— 这是最坑的一条。
   打包机（我这边）没装 `websocket-client` 时，PyInstaller 只打一条警告就过去了，
   产物**双击能开、GUI 也能开**，但一连 OBS 就：
   `RuntimeError: 缺少 websocket-client，请先 pip install websocket-client`
   —— 也就是"别人拿到就是不能用"，而且完全看不出是打包问题。
   修法（`build_exe.py`，两道闸）：
   * **打包前** `preflight_deps()`：这台机器 `import websocket` / `import tkinter` 失败就直接
     `return 2` 拒绝打包（并告诉对方装什么）；
   * **打包后** `verify_built_exe()`：拿**真的 exe** 跑 `--selftest`，退出码非 0 就
     `return 3` 并提示"先别拷给别人"。
   引擎侧也加了 `--selftest`（验 websocket-client / tkinter / 键位表 / 内存公式，并列出外部条件）。
   实测：修好后 `开始导播.exe --probe` 的错误从"缺库"变成正常的
   `❌ 连不上 obs-websocket: [WinError 10061]`（OBS 没开）。
1. **onedir 产物文件夹被占用 → `os.rename` 报 `WinError 183`**：
   上一轮测试启动的「开始导播.exe」还在跑（占着 `_internal\*.dll`），
   `shutil.rmtree(ignore_errors=True)` 静默失败，于是 `os.rename` 撞上已存在的目录。
   → `_rmtree_or_die()`：删完再检查一次，还在就直接报
   "最常见的原因：正在运行的「开始导播.exe」没关"，而不是丢一个 WinError 出来。
   （打包前记得先关掉正在跑的成品 —— 包括它打开的设置窗口。）
2. **带 BOM 的 config.json 会让引擎起不来**：记事本 / PowerShell `Set-Content -Encoding utf8`
   存出来的文件开头有 `\ufeff`，`open(..., encoding="utf-8")` 直接 `JSONDecodeError`。
   → `load_config()` 改用 **`encoding="utf-8-sig"`**（BOM 和无 BOM 都能读）。
   `save_config()` 仍然写**不带 BOM** 的 UTF-8。
3. **内存估算单位**：一开始用 1024 进制（GiB）算，得到 4.63 "GB"，和文档里记的 4.98 GB 对不上。
   → 统一用**十进制 GB**（`/1e9`），这样和 `双机导播方案.md`（40.86 GB → 12.51 GB）里
   任务管理器读到的数字一致，不会让人以为算错了。
4. **preflight 里那次"冲旧缓冲"会立刻分配第二份**（`ReplaySource.Replay` → 取出一段）。
   回放功能关着或 armed 模式下**不能**再无条件做这件事，否则"一启动就 2×"的旧行为会回来。
   现在：关着 → Disable；armed → Disable 等按入点键；只有 buffer 模式才冲。
5. **双击行为变了之后要补回"开箱即用"**：改成"双击开设置窗口"后，第一次用的人
   直接点「启动引擎」会因为 `config.json` 还不存在而连不上 OBS。
   → GUI 里两处补齐：启动时若旁边没有 `config.json`，`after(300ms)` 弹一句
   "现在运行首次设置向导吗"；点「启动引擎」时若还没有配置，直接提示先做向导
   （并顺手问一句要不要现在就跑）。

## 十一、2026-10-08：死机排查 —— "电脑总是死机，是不是这个软件搞的？"

### 11.1 结论先行

**是（在 4K 画布 + 默认 10 秒的情况下，一定会）。** 不是"我们的进程泄漏"，
而是**我们把回放插件配成了一台机器根本装不下的规格**：

```
插件缓冲 = 画布宽 × 高 × 4 字节 × 帧率 × 秒数 × 2 份
真机取证那台：3840×2160 × 4 × 60 × 10 × 2 = 39.81 GB     而它只有 31.47 GB 内存
```

后果不是"某个程序崩了"，而是**整机级换页**：内存被吃光 → 硬盘疯狂交换 →
所有程序（包括系统 shell）失去响应 → 用户只能长按电源键。这正好解释现场的所有现象：

| 现场现象 | 与"内存换页风暴"是否吻合 |
|---|---|
| `Kernel-Power 41` 但 **BugcheckCode = 0**（没有蓝屏） | ✅ 硬挂/强制断电才这样；换页风暴不产生转储 |
| 事件日志里**没有任何** `WHEA-Logger`（硬件报错） | ✅ 排除 CPU/内存/PCIe 硬件故障 |
| 事件日志里**没有** `Display 4101`（显卡驱动 TDR） | ✅ 排除显卡驱动复位 |
| `Application Hang`：**obs64.exe 停止与 Windows 交互并已关闭** | ✅ OBS 自己先被拖死，典型 OOM/换页 |
| 崩溃转储只有几个月前的，近期没有 | ✅ 没有蓝屏过，是挂起/断电 |

### 11.2 取证怎么做（`tools/diagnose_freeze.ps1`，只读）

不取证就是瞎猜。仓库里现在有 `tools/diagnose_freeze.ps1`（**只读**，只在桌面写一个 txt）：
机器内存 / 页面文件、**OBS 画布与帧率（直接读 `basic.ini`，据此算出插件要多少 GB）**、
系统日志里 `Kernel-Power 41`（带 BugcheckCode）、`WHEA`、`Display 4101`、
`disk 129/153`、`Resource-Exhaustion-Detector`、`Application Hang`、
崩溃转储、以及第三方输入层（`inputx64`/interception/Parsec/ToDesk 这类）。

判读口诀：
* `BugcheckCode=0` + 无 WHEA + 无转储 → **硬挂或断电**，不是蓝屏；
* 有 `Resource-Exhaustion-Detector 2004`、或 OBS/浏览器被"停止交互" → **内存被吃光**；
* 有 `WHEA` → 硬件层，与本软件无关；
* 有 `Display 4101` → 显卡驱动，先更新驱动再看。

### 11.3 护栏：把"能发生"变成"不可能发生"（`memory_guard`，默认开）

光"回放功能默认关"不够 —— 用户一打开就还是会死。所以：

1. **`plan_replay_seconds()`**（纯函数，可单测）：按 `总内存 30% / 可用内存 60%` 取安全预算，
   把"想要的时长"降到装得下的最大值（步长 0.5 秒，下限 2 秒）；
2. **`_apply_memory_guard()`** 在 preflight 里、**写插件 duration 之前**跑：
   * 装得下 → 不动；
   * 装不下 → **自动降时长**（并写回 config.json）＋打印"根因是画布太大"和一键降画布命令；
   * 高分辨率画布（≥2560 宽）且只能攒 < 4 秒 → **直接拒绝开回放**（2 秒的回放没有使用价值，
     不如明说"先降画布"）；连 2 秒都装不下 → 同样拒绝；
3. **`set_replay_enabled(True)` 也会先过护栏** —— 手机页面/图形界面随时能开回放，
   不能只靠启动那一次检查；
4. **图形界面的估算标签**改成用 **OBS 配置里的真实画布**（`canvas_from_obs_config()`
   读 `%APPDATA%\obs-studio\basic\profiles\*\basic.ini` 的 `BaseCX/BaseCY/FPSCommon`），
   并直接显示 `⛔ 内存护栏：本机内存 33.8 GB，这一套设置装不下（峰值要两份 ≈ 39.8 GB）`。
   以前 GUI 按 1080p 估，4K 时会**低估 4 倍**，正好掩盖了死机原因。
5. 回归：`--simulate` 里有一段纯函数回归，覆盖
   `4K60/10s/32G`、`4K60/10s/64G`、`1080p60/10s/32G|16G|8G`、`4K60/2s/8G` 六种组合。

### 11.4 与本软件无关的死机怎么区分

`Kernel-Power 41` 且 `BugcheckCode=0` 的另一大类原因是**硬件/电源**：
内存不稳（XMP）、电源老化、主板、过热、外设（采集卡/USB 控制器）。
区分办法就一条、但很硬：**关掉本软件（连 OBS 插件都不用）跑同样时长，看还死不死**。
按时间轴对照即可 —— 引擎/OBS 在跑的时候才死 = 相关；不开也死 = 与本软件无关。

> 顺带记一笔现场看到的噪声（**都不是死机原因**，但容易被误读）：
> `usbperf 2001`（USB 性能计数器坏了）、`Search 3006/3007/10021`（索引器计数器）、
> `GCUbridge` 的 MQTT `NullReferenceException`（某个第三方 .NET 服务自己崩）。
> 另外 `Service Control Manager 7000：inputx64 服务启动失败，此驱动程序被阻止加载`
> 值得单独留意 —— 它是**输入类驱动**，如果死机时伴随键鼠失灵，要把它和我们引擎的
> 全局键盘钩子（`WH_KEYBOARD_LL`）一起对照排查。
